# Upstream v1.18.2 StartOS Preparation Design

## Goal

Extend the existing Start9 Community intake work from upstream Hashrate Autopilot v1.18.0 to the latest stable v1.18.2 release and leave a locally verified `1.18.2:0` candidate ready for the existing Community pull-request pipeline.

## Integration Base

Use `Start9-Community/hashrate-autopilot-startos` branch `chore/upstream-v1.18.0` as the base. It contains the accepted Community intake direction, including package ID `hashrate-autopilot`, dependency wiring, package documentation, and workflow conformity. Preserve upstream history by merging annotated upstream tag `v1.18.2` with `--no-ff`.

## Conflict Policy

Take upstream for application-owned paths, including `packages/`, general `docs/`, lockfile inputs, Umbrel files, and application changelog entries. Preserve the Community branch for the StartOS-owned surface: `startos/`, `Dockerfile.startos`, `Makefile`, `tsconfig.json`, `icon.png`, package documentation, and Community workflows.

Retain the fork-only package constraints documented in `AGENTS.md`: Node 22 types, workspace package rewrites, `linkWorkspacePackages`, dependency host imports, Bitcoin cookie credentials, strict dependency-address failures, and DRY-RUN as the first-run mode.

## Release Adaptation

Set `startos/utils.ts` to upstream application version `1.18.2` and `startos/versions/current.ts` to ExVer `1.18.2:0`. Rewrite all five localized release-note entries to cover the v1.18.1 unpaid-history protection/recovery and v1.18.2 marketplace account-protection and truthful hold/failure reporting. Link the complete upstream v1.18.2 release notes.

Review every upstream configuration and image-input change between v1.18.0 and v1.18.2. Do not inject operator-owned settings. Preserve DRY-RUN and do not perform live marketplace mutations during automated testing.

Keep the upstream Umbrel manifest and image pin synchronized as part of the upstream merge. Update StartOS README and root instructions only where the new behavior changes StartOS-specific support or operating guidance.

## Validation and Evidence

Use the repository's native gates: locked dependency install, lock consistency, lint, TypeScript checks, complete tests, SDK lint, and both `make x86` and `make arm`. Inspect each resulting `.s9pk` for package ID, ExVer, architecture, image, release notes, and source hash; record SHA-256 checksums. Run the Community audit before and after the change.

Treat hosted CI and device lifecycle results as separate evidence. Do not infer them from local builds. Any device validation must preserve DRY-RUN and avoid creating, editing, or cancelling marketplace bids.

## Publishing Boundary

Do not push a branch or tag to Start9-Community, open or modify its pull requests, publish a release, or request promotion. The prepared branch is a handoff for the existing PR chain. Start9's merge automation owns the canonical tag, build, GitHub release, and `community-beta` deployment.
